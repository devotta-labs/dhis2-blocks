This preview reads one person in the WHO RMNCH Tracker in the Sierra Leone

attributes, a tag for a person who is inactive or a possible duplicate, and

those say "Not recorded" rather than leaving a gap. Copy the example's code
to start from it, and edit the uids at the top of the file.

## Usage

Wrap a banner in `TrackedEntityHeaderProvider` with the tracked entity and the
program. `trackedEntity` is the only required prop; without `program` the
banner shows only the tracked entity type's attributes, and the owner and enrollment
parts say they need one.

```tsx
import {
    TrackedEntityBanner,
    TrackedEntityHeaderProvider,
} from '@/components/tracked-entity-header'

export function RecordHeader({ trackedEntityId }: { trackedEntityId: string }) {
    return (
        <TrackedEntityHeaderProvider
            trackedEntity={trackedEntityId}
            program="WSGAb5XwJ3Y"
        >
            <TrackedEntityBanner />
        </TrackedEntityHeaderProvider>
    )
}
```

The parts load the tracked entity and the program's attribute metadata through
the DHIS2 app runtime, once for every part inside the provider. Values are
shown as DHIS2 shows them: option names rather than codes, and dates in the
system's calendar. A value the record doesn't have says "Not recorded", and
one that can't be read says "Unavailable". The banner draws its own loading, failed, restricted and not
found states, and never shows the previous record while the next one loads. A
record that has loaded stays on screen if a later refresh fails, unless access
has been withdrawn. Program metadata and organisation unit names are kept for
an hour.

## Framing the banner

The banner draws its background and padding but no edge, so it fits wherever
you put it. Add the edge with `className`: a bottom border for a bar across
the top of a page, or a border and rounded corners for a card. Your padding
replaces the banner's, so a bar can line up with the page's own margins.

Across the top of a page:

```tsx
<TrackedEntityBanner className="border-b border-dhis2-border-strong px-6" />
```

As a card:

```tsx
<TrackedEntityBanner className="rounded-dhis2-md border border-dhis2-border-strong" />
```

## Composing a banner

Place parts inside `TrackedEntityBanner` to choose what it shows. Line one is
everything up to the facts, and the facts take line two. The toggles for
**Details** and **Related** share the line below, each with how many rows it
holds, and each opens its list under them. Place `TrackedEntityDetails` and then
`TrackedEntityRelationships` last, after the other parts, so the order a
keyboard or screen reader follows matches the screen. Inside a banner their
`className` goes to the toggle. `TrackedEntityActions` sits in a column of its own on the right, wherever
you place it, so a long line one wraps beside it. In a narrow banner the actions
move below everything.

```tsx
<ObservationsProvider trackedEntity={personId} program="WSGAb5XwJ3Y">
    <TrackedEntityHeaderProvider trackedEntity={personId} program="WSGAb5XwJ3Y">
        <TrackedEntityBanner className="sticky top-0">
            <TrackedEntityName attributes={['w75KJ2mc4zz', 'zDhUuAYrxNC']} />
            <TrackedEntityStatus />
            <TrackedEntityDate attribute="gHGyrwKPzej" label="Born" age />
            <TrackedEntityAttribute attribute="lZGmxYbs97q" label="ID" />
            <TrackedEntityEnrollment />
            <TrackedEntityOwner />
            <TrackedEntityActions>
                <Button size="sm" onClick={recordVisit}>
                    Record visit
                </Button>
            </TrackedEntityActions>
            <TrackedEntityFacts>
                <TrackedEntityAttribute attribute="gu1fqsmoU8r" />
                <ObservationInline
                    dataElement="vANAXwtLwcT"
                    label="Haemoglobin"
                    unit="g/dL"
                />
            </TrackedEntityFacts>
            <TrackedEntityDetails />
        </TrackedEntityBanner>
    </TrackedEntityHeaderProvider>
</ObservationsProvider>
```

Each value shows under its attribute's form name, and a hairline separates
the pairs. Form names are often long, so pass `label` to shorten one, as with
`label="ID"` above. `TrackedEntityAttribute`, `TrackedEntityDate`,
`TrackedEntityOwner` and `ObservationInline` take a `label`.

Place `TrackedEntityStatus` yourself when composing. Without it, an inactive
record is shown by the banner's muted surface alone, which is colour alone. A
banner with no children places it for you.

The banner is labelled by the `TrackedEntityName` you place. Without one it
takes the tracked entity type's name, such as "Person" or "Shipment". `TrackedEntityDetails` lists
every attribute no other part shows, so an attribute you place, even inside
`TrackedEntityFacts`, isn't repeated there.

Stickiness is the host's, since only the host knows its scroll container: pass
`className="sticky top-0"` as above.

The parts are `TrackedEntityName`, `TrackedEntityDate`,
`TrackedEntityAttribute`, `TrackedEntityStatus`, `TrackedEntityOwner`,
`TrackedEntityEnrollment`, `TrackedEntityFacts`, `TrackedEntityActions`,
`TrackedEntityDetails`, `TrackedEntityRelationship` and
`TrackedEntityRelationships`. Each takes a `className`. `TrackedEntityDate` takes
a date `attribute`, or `enrollmentDate="occurredAt"` or `"enrolledAt"` for a
date kept on the enrollment, labelled as the program labels it: a birth date
in a child programme, or "Dispatched" for a shipment. With `age`, the part
also shows the age in the system's calendar: days under one month,
months under two years, years after. A Coptic system shows no age, since the
calendar library can't convert Coptic dates.

The block can't tell what a date means, so `age` counts from whichever date
you give it to today. Give it a date where that count means something: a date
of birth for a person's age, or a manufacture date with `label="Age of vial"`.
On an enrollment date that means "registered", it counts the time since
registration, so label it that way rather than as an age. A date recorded in
an event isn't an attribute or an enrollment date, so this part can't read it.

The event facts, such as the haemoglobin above, come from
[Observation Cards](/blocks/observation-cards): `ObservationInline` needs an
`ObservationsProvider` above it, and shares its requests with the cards on the
same page.

## Relationships

Two parts show what a record is linked to. `TrackedEntityRelationship` is a
fact: one relationship type, by uid, labelled and named like any other value.
`TrackedEntityRelationships` is every link, one line per relationship type with
its count and the first three names.

```tsx
<TrackedEntityBanner>
    <TrackedEntityName attributes={['w75KJ2mc4zz', 'zDhUuAYrxNC']} />
    <TrackedEntityFacts>
        <TrackedEntityRelationship
            relationshipType="dDrh5UyCyvQ"
            label={{ from: 'Baby', to: 'Mother' }}
            hideWhenEmpty
            href={(id) => `/people/${id}`}
        />
        <TrackedEntityRelationship relationshipType="Mv8R4MPcNcX" />
    </TrackedEntityFacts>
    <TrackedEntityRelationships
        labels={{ m6XJSapEvOa: 'Linked cases' }}
        onSelect={openRecord}
        moreHref={(type) => `/links?type=${type}`}
    />
</TrackedEntityBanner>
```

A link is labelled from this record's end. A one-way type uses `fromToName` at
the `from` end and `toFromName` at the `to` end, and falls back to the type's
own name when that is not set, as "Focus to Case" does. Demo
types are named like `Mother-Child_a-to-b_(Person-Person)`, so every label can
be replaced. Pass a string to `label`, or to `labels` by type uid, for either
end. Pass `{ from, to }` when the type reads differently from each end: `from`
is the label when this record is the `from` end, so the mother's banner says
"Child" and the baby's says "Mother".

A one-way type can hold this record at either end. Without `end`, each end is
its own pair, labelled from its end. Pass `end="from"` or `end="to"` to show
one. For a bidirectional type `end` has no effect. `hideWhenEmpty` is for a
link most records won't have: with none, the part renders nothing instead of
"Not recorded". It hides only a known absence. A request that fails still says
"Unavailable".

Names are plain text. Pass `href` to make them real links, so ctrl- or middle-click opens a new tab.
Pass `onSelect` when your app routes itself: it is called with the linked
record's id on a plain click. With both, the link's default is prevented.
`moreHref` and `onMore` do the same for "and N more", with the relationship
type uid. A linked record the user can't read says "You don't have access to
this record", with no name and no link. A link whose other end is an event or an
enrollment is counted, not named, such as "2 events".

Inside a banner, `TrackedEntityRelationships` is a **Related** toggle with the
number of links, beside **Details**. It shows nothing while loading or when there are no links,
and "Unavailable" if the request fails. Outside a banner it is the list itself,
or "No related records". Both parts share one request for the record's links,
made only when one of them is placed, so a banner with no children makes none.

The block ships no peek. Build one from the Quick look parts: `onSelect` keeps
the linked id in your state, and a popover loads that record when it opens.

```tsx
const RelatedPeek = ({ trackedEntityId, programId }) => {
    const anchor = useRef<HTMLDivElement>(null)
    const [linked, setLinked] = useState<string>()
    return (
        <>
            <div ref={anchor}>
                <TrackedEntityHeaderProvider
                    trackedEntity={trackedEntityId}
                    program={programId}
                >
                    <TrackedEntityRelationships onSelect={setLinked} />
                </TrackedEntityHeaderProvider>
            </div>
            <Popover
                open={!!linked}
                onOpenChange={(open) => !open && setLinked(undefined)}
            >
                <PopoverContent anchor={anchor} aria-labelledby="peek-name">
                    {linked && (
                        <TrackedEntityHeaderProvider
                            trackedEntity={linked}
                            program={programId}
                        >
                            <QuickLook />
                        </TrackedEntityHeaderProvider>
                    )}
                </PopoverContent>
            </Popover>
        </>
    )
}
```

`QuickLook` is the component from the next section, with `id="peek-name"` on
its `TrackedEntityName`.

## Parts outside a frame

The banner is one layout, not a requirement. Every part works anywhere under
`TrackedEntityHeaderProvider`, so you can build a quick look popover or a
half-page summary from the same parts. Outside the banner you draw the
whole-record states yourself from `useTrackedEntityHeader()`, which returns
`status` (`'loading'`, `'failed'`, `'restricted'`, `'not-found'` or `'ready'`)
and `retry`:

```tsx
const QuickLookPopover = ({ trackedEntityId, programId }) => (
    <PopoverContent aria-labelledby="quick-look-name">
        <TrackedEntityHeaderProvider
            trackedEntity={trackedEntityId}
            program={programId}
        >
            <QuickLook />
        </TrackedEntityHeaderProvider>
    </PopoverContent>
)

const QuickLook = () => {
    const { status } = useTrackedEntityHeader()
    if (status !== 'ready') return <QuickLookStatus status={status} />
    return (
        <>
            <TrackedEntityName
                id="quick-look-name"
                attributes={[firstName, lastName]}
            />
            <TrackedEntityStatus />
            <TrackedEntityDate attribute={birthDate} />
            <TrackedEntityFacts>
                <TrackedEntityAttribute attribute={allergies} />
            </TrackedEntityFacts>
        </>
    )
}
```

Whatever you do, every value part renders nothing until `status` is
`'ready'`, so a restricted record never shows a name or a misleading "Not
recorded". Outside a banner `TrackedEntityActions` renders in every state, so
a "Request access" button still shows. Label your own container, such as a dialog or popover, with
`aria-labelledby` pointing at `TrackedEntityName`, which takes an `id`. Nothing
is asked for until a part or `useTrackedEntityHeader()` mounts under the
provider, so a popover loads the record when it opens.

## Finding attribute uids

Parts name attributes by uid. List a program's attributes, with which ones
show in lists:

```
GET /api/programs/<program>?fields=programTrackedEntityAttributes[displayInList,sortOrder,trackedEntityAttribute[id,displayName,valueType]]
```

## API reference

### TrackedEntityHeaderProvider

- `trackedEntity: string` — **required.** The tracked entity the banner shows.
- `program?: string` — the program whose attributes, enrollment and owner are
  shown. Changing either prop starts from nothing.
- `children?: ReactNode` — the banner and any of your own UI that uses
  `useTrackedEntityHeader`.

### TrackedEntityBanner

- `children?: ReactNode` — the parts to show. Without children, the program's
  list attributes, the tags and the details.
- `className?: string` — applied to the banner. Use it for the edge, which the
  banner doesn't draw, and to replace its padding.

The parts take `className` and the props listed in their types.
