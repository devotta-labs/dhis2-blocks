## Usage

Pass the program and what to do with the person the user picks, then place
the parts you need. `program` and `onSelect` are the only required props.

```tsx
import {
    FinderField,
    FinderForm,
    FinderHint,
    FinderProvider,
    FinderResults,
    FinderSubmit,
    type FinderPerson,
} from '@/components/tracked-entity-finder'

export function FindPatient({
    onSelect,
}: {
    onSelect: (person: FinderPerson) => void
}) {
    return (
        <FinderProvider program="WSGAb5XwJ3Y" onSelect={onSelect}>
            <FinderForm>
                <FinderField attribute="lZGmxYbs97q" />
                <FinderHint />
                <FinderSubmit />
            </FinderForm>
            <FinderResults />
        </FinderProvider>
    )
}
```

`onSelect` receives the person: `trackedEntity`, `trackedEntityType`,
`orgUnit`, `programOwner` (the organisation unit that owns the person in
this program, when known), and `attributes`, a map from attribute uid to
value. Searches cover every organisation unit the user
can search.

## Finding attribute uids

Fields name program attributes by uid. List a program's attributes, with
which are searchable and which are unique IDs:

```
GET /api/programs/<program>?fields=name,minAttributesRequiredToSearch,programTrackedEntityAttributes[searchable,displayInList,trackedEntityAttribute[id,displayName,valueType,unique]]
```

Only attributes marked `searchable` in the program can be used.

## The rules

The finder applies the program's search settings from DHIS2. You choose the
fields; you cannot loosen these rules:

- **Minimum details.** The program's "attributes required to search" sets how
  many details the user must fill in. Until then, Search stays disabled and
  `FinderHint` says how many are missing. A minimum of 0 still needs one
  detail, so an empty form never searches.
- **IDs search alone.** A unique attribute, such as a national ID, can search
  on its own, and always matches exactly. When an ID is filled in, the search
  uses the ID only and the form's other filled fields aren't sent. A form
  searches by one ID at a time.
- **Exact matches.** Option sets, numbers, yes/no and dates match exactly.
  Text matches the way the attribute is set up to be searched, and needs the
  attribute's minimum number of characters.
- **Several options.** For an attribute that holds several options (value
  type MULTI_TEXT), the user can pick more than one, and the search finds
  people who have every option picked. This needs DHIS2 2.43 or later; on an
  older server the field isn't searched, because DHIS2 compared the whole list.
- **Too many matches.** When more people match than the program allows, the
  results ask the user to add another detail instead of listing them.

## Forms and fields

`FinderForm` groups the fields of one search. Enter submits it. Inside it:

- `FinderField attribute="uid"` shows the attribute's label and an input that
  fits its type: text, an option set, a multi-select for several options,
  yes/no, a checkbox, a number, or a date in the server's calendar. Set `label`, `description` or `placeholder` to
  change the defaults.
- `FinderRangeField attribute="uid"` shows From and To inputs for number,
  date, date-time and age attributes.
- `FinderHint` shows what the form still needs, such as "Add 1 more detail to
  search". Place it where your users will read it.
- `FinderSubmit` is the Search button. It takes the props of the `Button`
  component, except `type`, and its children replace the label.

`FinderField` and `FinderRangeField` take `className` and the props listed
here, not every HTML prop. Each `FinderForm` is a [TanStack Form](https://tanstack.com/form),
and each field checks its value with a Zod schema built from the attribute's
metadata. A field shows its own error, such as a date that doesn't exist, once
the user leaves it or tries to search. While a field has an error, the form
won't search, and pressing Search shows every error in the form.

Several forms can share one provider, like the ID form and the **No ID?** form
above. Each form keeps its own values, and the results show the last search
until the next one.

## Results

`<FinderResults />` with no children shows the default results: a searching
state, "No one found", "Too many matches. Add another detail.", request
errors, a row per person with the program's list attributes, and paging.

With children, only the parts you place render. `FinderEmpty`,
`FinderTooMany`, `FinderSearching` and `FinderError` take children to replace
their text. `FinderList` repeats its children for each person, and inside it
`FinderValue attribute="uid"` shows one of the person's values, formatted for
its type:

### Hooks

For your own parts inside `FinderProvider`:

- `useFinderField(uid)` and `useFinderRangeField(uid)` — inside a
  `FinderForm`: `field`, the attribute's TanStack field; the attribute (with
  its `kind`, which says which value shape `field.handleChange` takes; an
  option set is `option` even on a TEXT attribute, and a MULTI_TEXT one is
  `multiText`, holding `codes`); `error`, the text to show
  once the user has left the field or tried to search; and `metadataError`,
  set when the field doesn't fit the program.
- `useFinderForm()` — inside a `FinderForm`: its TanStack form, for its
  values, `Subscribe` and `reset`.
- `useFinderSearch()` — inside a `FinderForm`: whether it can search, how
  many details are missing, and `submit`.
- `useFinderResults()` — the results status, the people on the page, paging,
  and `select`.
- `useFinderPerson()` — inside `FinderList`: the current person.
- `useFinderProgram()` — the program's name and searchable attributes.

### Custom fields

A field of your own counts toward the search like the built-in ones, as long
as it comes from `useFinderField` or `useFinderRangeField`. You get the
attribute's TanStack field and use it as you would in any TanStack form. For
example, a village stored as text but picked from a region and district tree:

```tsx
const VillageField = () => {
    const { field, attribute, error, metadataError } =
        useFinderField('villageUid')
    if (metadataError) return <p>{metadataError}</p>
    const value = field.state.value
    return (
        <VillagePicker
            label={attribute?.label}
            value={value?.kind === 'text' ? value.text : ''}
            onChange={(village) =>
                field.handleChange({ kind: 'text', text: village })
            }
            onBlur={field.handleBlur}
            error={error}
        />
    )
}
```

Its value is checked by the same Zod schema, counts toward the program's
minimum, and is searched with the attribute's operator. `error` is already
translated and waits until the user leaves the field; for something else,
read `field.state.meta` yourself.

## Metadata errors

A field that doesn't fit the program's metadata, such as an attribute that
isn't in it or isn't searchable, is left out of the search and shows a message
in its place. The rest of the form keeps working. The same attribute as both
`FinderField` and `FinderRangeField` in one form is a metadata error too; in
separate forms it's fine. A form that can never search,
because it has no usable ID field and too few usable fields for the
program's minimum, shows the message for the whole form.

In development, the message says what is wrong and lists the program's
searchable attributes with their uids and its minimum, so you, or your coding
agent, can fix the field. In production builds, users see "This search isn't
set up correctly" and the built-in parts log the full message to the console.
A custom field's `metadataError` is the same text: the full message in
development, the short one in production.

## API reference

### FinderProvider

- `program: string` — **required.** The tracker program to search.
- `onSelect: (person: FinderPerson) => void` — **required.** Called with the
  person the user picks.
- `children?: ReactNode` — the forms, results and any of your own UI that uses
  the hooks. The provider renders only its children.

`FinderField` and `FinderRangeField` take `className` and their listed props.
`FinderSubmit` takes `Button` props. The other parts accept `className` and
the props of their HTML element.
