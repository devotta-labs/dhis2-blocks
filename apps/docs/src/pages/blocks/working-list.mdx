## Basic usage

Compose the view switcher, toolbar controls, actions, and records table to
fit your users' workflow. `programId` and `orgUnitId` are the only required
props.

```tsx
import {
    WorkingList,
    WorkingListColumnSelector,
    WorkingListFilterControls,
    WorkingListTable,
    WorkingListToolbar,
    WorkingListToolbarActions,
    WorkingListViewSwitcher,
} from '@/components/working-list'

export const BasicWorkingList = () => (
    <WorkingList
        programId="IpHINAT79UW"
        orgUnitId="y77LiPqLMoq"
        defaultPagination={{ page: 1, pageSize: 10 }}
    >
        <WorkingListViewSwitcher />
        <WorkingListToolbar>
            <WorkingListColumnSelector />
            <WorkingListFilterControls />
            <WorkingListToolbarActions />
        </WorkingListToolbar>
        <WorkingListTable />
    </WorkingList>
)
```

## Live metadata

The Working List needs no fixture data — it reads programs, tracked entity
metadata, records, filters, sorting, pagination, and saved views from the
connected instance. This example drives `programId` from live metadata and
the signed-in user's organisation units, so it works on any backend:

## State and composition

`WorkingList` runs uncontrolled by default: it owns the selected saved view
and pagination while the host supplies `programId`, `orgUnitId`, and the
composition. Provide `viewId` + `onViewChange` and `pagination` +
`onPaginationChange` to control that state yourself — for example to persist
it in the URL.

`WorkingList` keys its internal list instance by `programId`, so changing
programs remounts the list and each program starts from clean uncontrolled
state. The examples above additionally pass `key` on the block itself to
remount the whole composition. Saved views are loaded
from and written to the real server; mutations appear after a reload.
