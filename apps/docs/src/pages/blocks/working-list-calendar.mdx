The calendar is another way to look at a [Working List](/blocks/working-list):
the same saved view, filters and organisation unit, with each record placed on
one of its dates. It answers "who is due this week?" or "what happened on the
14th?" at a glance.

## Installation

<InstallCommand item="working-list-calendar" />

This also installs the Working List block.

## Usage

Render `WorkingListCalendar` inside `WorkingList`, beside or instead of
`WorkingListTable`, and compose its parts:

```tsx
import {
    WorkingList,
    WorkingListToolbar,
    WorkingListFilterControls,
} from '@/components/working-list'
import {
    WorkingListCalendar,
    WorkingListCalendarDayRecords,
    WorkingListCalendarDisplayToggle,
    WorkingListCalendarGrid,
    WorkingListCalendarNavigation,
} from '@/components/working-list-calendar'

export const AppointmentsCalendar = () => (
    <WorkingList programId={programId} orgUnitId={orgUnitId}>
        <WorkingListToolbar>
            <WorkingListFilterControls />
        </WorkingListToolbar>
        <WorkingListCalendar onRecordClick={(record) => openRecord(record)}>
            <div className="flex items-center gap-2">
                <WorkingListCalendarNavigation />
                <WorkingListCalendarDisplayToggle className="ms-auto" />
            </div>
            <WorkingListCalendarGrid />
            <WorkingListCalendarDayRecords />
        </WorkingListCalendar>
    </WorkingList>
)
```

The grid shows full weeks, so the first and last rows include days from the
neighbouring months, muted but with their records. Selecting a day lists all
of its records in `WorkingListCalendarDayRecords`, where `onRecordClick` opens
them with the same record target as the table's `onRowClick`. On a wide
calendar the day list takes a column of its own beside the grid; place it
anywhere else inside `WorkingListCalendar` and pass a `className` to suit.

The calendar reads the list's filters but never changes them. Switching
between table and calendar leaves the saved view and the table's page as they
were. If a saved filter limits the dates, the calendar opens inside them and
stops at their edges. When the selected saved list cannot load, the calendar
offers the same repair or way back to the default list as the table.

## What each day shows

By default each day counts its records by status: "6 Active, 2 Completed".
For a busy clinic that says more than a column of names. Users switch to
names with `WorkingListCalendarDisplayToggle`; leave it out and the calendar
stays on the display you chose. `defaultDisplay="records"` starts on names,
and `display` with `onDisplayChange` keeps the choice yourself, for example
in the URL or the user's settings.

The grid's children are what each day shows under its number. The default is
`WorkingListCalendarCellRecords`, which shows up to `max` status counts
(largest first) or `max` names, 3 by default, with the records left over on
a "+N more" row:

```tsx
<WorkingListCalendarGrid>
    <WorkingListCalendarCellRecords max={5} />
</WorkingListCalendarGrid>
```

For something else, write a cell part of your own with
`useWorkingListCalendarDay()`, which gives it the day it draws. A plain count
of the day's records, without statuses, is a few lines:

```tsx
const DayCount = () => {
    const { day } = useWorkingListCalendarDay()
    if (day.records.length === 0) return null
    return <span>{day.records.length} records</span>
}

;<WorkingListCalendarGrid>
    <DayCount />
</WorkingListCalendarGrid>
```

## Status colours

Records are coloured and counted by status. For tracked entities that is the
enrollment status; for events it is the event status, with scheduled visits
before today counted as overdue. Pass `recordStatus` for a rule of your own,
returning an `id` to count by, a `label` and a `tone` (`neutral`, `info`,
`positive`, `warning` or `critical`):

```tsx
<WorkingListCalendar
    recordStatus={(row, cellText) => {
        const risk = cellText(riskAttributeId)
        return {
            id: risk,
            label: risk,
            tone: risk === 'High' ? 'critical' : 'neutral',
        }
    }}
>
    {/* … */}
</WorkingListCalendar>
```

## Weekends

Pass the days that count as the weekend, as ISO weekdays (1 is Monday, 7 is
Sunday), and how their columns show. Weekends differ by country, so there is
no default:

```tsx
<WorkingListCalendarGrid weekend={[5, 6]} weekendColumns="narrow" />
```

`narrow` keeps the columns but shows only counts in them; `hide` removes
them and says above the grid how many records fall on the hidden days.

## Record names

Each record is named by the first two columns of the list that have a value,
in the order users see them in the table and formatted the same way: option
names rather than codes, dates in the system calendar. The calendar's own
date column is left out, and a record with nothing to show reads "Unnamed
record". Changing the visible columns or their order changes the names.

When your app knows its own model, pass `recordLabel`. It gets the row and
a `cellText(fieldId)` helper that formats any field as the table does:

```tsx
<WorkingListCalendar
    recordLabel={(row, cellText) =>
        `${cellText(caseIdAttributeId)} · ${cellText(nameAttributeId)}`
    }
>
    {/* … */}
</WorkingListCalendar>
```

## Which date places a record

`dateField` picks the date:

| `dateField`                 | Lists            | Date            |
| --------------------------- | ---------------- | --------------- |
| `enrolledAt` (default)      | Tracked entities | Enrollment date |
| `enrollmentOccurredAt`      | Tracked entities | Incident date   |
| `eventOccurredAt` (default) | Events           | Report date     |
| `eventScheduledAt`          | Events           | Scheduled date  |

A field that does not fit the list's current mode falls back to that mode's
default, so the calendar keeps working when the user switches between a
tracked-entity and an event view.

```tsx
<WorkingListCalendar dateField="eventScheduledAt">
    {/* … */}
</WorkingListCalendar>
```

## Selected day

The selected day is uncontrolled by default; `defaultSelectedDay` sets the
first one. To keep it yourself, for example in the URL, pass `selectedDay` and
`onSelectedDayChange` together. Days are system-calendar dates written
`YYYY-MM-DD`.

```tsx
<WorkingListCalendar selectedDay={day} onSelectedDayChange={setDay}>
    {/* … */}
</WorkingListCalendar>
```

## Your own layout

`useWorkingListCalendar()` inside `WorkingListCalendar` returns the visible
month's weeks, each day's records, the selection and the loading state.
Clearing the selection keeps the month in view.

```tsx
import { useWorkingListCalendar } from '@/components/working-list-calendar'

const BusiestDay = () => {
    const { weeks, dayName } = useWorkingListCalendar()
    const busiest = weeks
        .flat()
        .filter((day) => day.isInCurrentMonth)
        .sort((a, b) => b.records.length - a.records.length)[0]

    return busiest ? <p>Busiest: {dayName(busiest)}</p> : null
}
```

## Boundaries

- Only the four system dates above can place records. Attribute and data
  element dates have no date filter on the DHIS2 tracker API.
- The calendar loads at most 1000 records for the weeks on screen (`limit`),
  including the neighbouring months' days, and says so when they hold more.
- Coptic instances are not supported yet: the date picker in
  `@dhis2/multi-calendar-dates` cannot show Coptic dates, so the calendar says
  so and the table stays the way to see the list.
- Months only: there is no week or day layout. The month and year selects
  jump anywhere; previous and next stop at a saved filter's dates.
