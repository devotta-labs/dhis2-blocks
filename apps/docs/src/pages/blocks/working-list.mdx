Working List brings your DHIS2 records into a table or calendar, so you can
find people, review visits, and focus on the work that needs attention.

<ExampleCard slug="working-list/default" />

The examples use the Sierra Leone demo data.

## Find the records you need

Filter by the fields in your program, sort the results, and choose which
columns to show. Save useful combinations as views to return to them later,
or download the visible rows.

Saved views belong to your DHIS2 instance. Changes to them also apply when
you use those views in other apps.

Your app can make a record open its details when selected; the examples
here keep records read-only.

## Choose a program and organisation unit

Let users switch between the programs and organisation units they have
access to.

## Calendar view

See when activity happens and which days are busiest. Switch between table
and calendar without changing your saved view or filters.

<ExampleCard slug="working-list/calendar" />

Select a day to see its records. Show names or status counts, and choose the
date that matters to your work: enrollment or incident dates for people,
report or scheduled dates for events. Weekend columns and status colours
can be adjusted to fit your program.

Dates follow your DHIS2 calendar, including Ethiopian and Nepali. Coptic is
not supported. The calendar loads up to 1,000 records at a time and warns
you when there are more.

[Try the playground](/playground/working-list?display=calendar) to explore
different dates, layouts and loading states.

## Build your own parts

`WorkingList` keeps only what the person has chosen: the view, the changes
they have not saved, and the page. Leave `viewId` and `pagination` out and it
keeps them itself, or pass each with its `onViewChange` or
`onPaginationChange` to keep them in your app, in the URL for example. A page
you pass is the page the list opens on. After that, a new view or
organisation unit starts on page 1 and tells `onPaginationChange`.
`onDirtyChange` tells you when there are unsaved changes, so you can warn
before the person leaves.

Anything rendered inside `WorkingList` can read and change that state, and
load what the server holds for it:

- `useWorkingList()` returns `programId`, `orgUnitId`, `viewId`, `draft` and
  `pagination`, with `selectView`, `setDraft` and `setPagination` to change
  them.
- `useWorkingListMetadata()` loads the program and its fields.
- `useSavedLists()` loads the program's saved lists.
- `useWorkingListView()` returns the selected view: its saved list, the
  configuration on screen and `isDirty`.
- `useWorkingListRecords()` loads the page of records on screen.
- `useCreateSavedList()`, `useUpdateSavedList()`, `useDeleteSavedList()` and
  `useRepairSavedList()` save changes. Each is a TanStack Query mutation, and
  reloads the saved lists when it is done.

The loading hooks return `isPending`, `isError` and `data`, so a component
handles its own loading and error states:

```tsx
const UnsavedChanges = () => {
    const view = useWorkingListView()

    if (view.isPending) return <Skeleton />
    if (view.isError) return <WorkingListSelectionError />
    return view.data.isDirty ? <p>Unsaved changes</p> : null
}
```
